# Change-scoped gallery validation

Pages keeps the exact publication/unchanged-original gate, static contracts, Three.js parsing, build and release inventory audit. Every normal run also checks every bilingual static detail/download/credit payload, the full key-interaction probe, and direct detail plus one complete desktop thumbnail → real GLB → canonical return round trip. `QA_HANDOFF_SMOKE=1` selects those existing handoff cases; default invocation still runs every case and assertion.

`Full release review` runs independent browser probes in parallel. `site/ci-scope.mjs` selects work from the PR base or push-before SHA, failing closed to full review when provenance is unavailable. Runtime changes exercise all models, the language/theme/viewport matrix, resource/failure recovery, handoff, modal and small-life suites. Published payload changes exercise model/download checks and preview reproduction. Only explicitly allowlisted prose paths omit the browser matrix; unknown or unpublished candidate paths conservatively require full review. The publication manifest selects the exact authorized set; it is not inferred from neighboring candidates. Manual dispatch runs all original probes, including every forced-fallback model. No failing assertion is suppressed.

`Review gallery in Chromium` remains a manual isolated review entry for both strict GPU and forced fallback. It now builds from the checked publication, which pairs accepted revision GLBs with their sealed revision image paths. Previously it mixed original-ten source metadata with the mixed-release image index and failed at natural-arch/structural-r002 before Chromium could run. It still marks output review-only and cannot deploy.

The asset pipeline tests remain independently scoped to scripts, schemas, skills and their fixtures. Existing dedicated render, hover and modal comparison workflows remain available. Deployment permissions and repository protection are unchanged. Browser screenshots are inspection evidence, not automatic art or scientific approval.

## Deterministic routing and validated-output reuse

The routing table is conservative and executable (`site/ci-scope.mjs`):

- Only the exact README filenames and Markdown under `docs/` are prose-only. File extensions elsewhere do not exempt a change.
- Published GLB/Blend/preview files, owned asset directories and matching poster files select their published asset IDs. A manifest addition selects the added/changed IDs; removal or shared publication-only changes require full coverage.
- Shared runtime, renderer, camera/light, tests, workflow, package scripts, toolchain, schemas and validator changes require the full matrix. Unknown paths and unavailable diff/base provenance also require full coverage.
- Pages still performs the publication/output gates and normal acceptance probes for every newly validated tree. Full release review runs its build, capture and inventory audit once in `prepare`, then every selected original browser task consumes that same immutable run artifact. No assertion is removed from the selected suites.

A main push may reuse a PR build only when all these independent checks succeed:

1. GitHub identifies the main commit as a merged same-repository PR; forks are never eligible.
2. Both the Pages and Full release review workflows completed successfully for that PR head. Their GitHub-owned check suites must report success and the `github-actions` app. A receipt cannot assert its own success.
3. Each receipt names the exact tested PR merge commit, its base/head parents, Git tree, run ID/attempt and runtime configuration. Both validated trees must exactly equal the main checkout tree, and both workflows must have tested the same merge commit. A new merge result or changed base therefore misses safely.
4. Validation control files must be identical to the PR base, including workflows, CI scripts, validator/test modules, executable QA helpers, package/lock/config files and the golden-poster contract. Runtime code under test remains eligible only after the full scoped checks pass; it cannot change the trusted test entrypoints. A PR that changes its own gate or receipt producer cannot qualify itself for reuse. The first deployment of this mechanism runs full verification.
5. The downloaded immutable artifact's SHA-256 must equal the digest returned independently by GitHub. Its members are allowlisted; the inner payload hash is checked; extraction rejects links, devices, absolute paths and traversal. Artifact contents are never executed by the reuse checker. A read-only Actions token is supplied only on main, never to this step in a PR.

Any unavailable API, missing/expired receipt, different tree/base/config, failed/incomplete check, modified policy or hash mismatch falls back to full verification, including the full main-branch browser matrix. Proof lookup has a two-minute network deadline, so unavailable evidence cannot stall a release indefinitely. There is no manual “looks similar” override. `qa/ci-provenance/reuse.json` records the source SHA/tree, comparison bases, check-suite IDs/results, artifact hashes and runtime configuration supporting a hit.

Deployment still depends on the Pages build job and uses the existing GitHub Pages environment and permissions. A complete output inventory/poster audit and pre-deploy handoff smoke still run on reuse; the existing deployed-site Chromium smoke runs after every deployment. No merge approval, branch protection or deployment authorization is changed. The lookup jobs add only read-only Actions, Checks and Pull requests metadata access; deployment write scopes remain unchanged.

### Publication memo within one job

The first `npm run build` publication gate always executes. If the checkout is clean, it writes a source/tree/manifest/runtime/run-bound memo outside the repository in `RUNNER_TEMP`. Repeated output audits in that job may use it only while the complete tracked checkout is unchanged. Repository-authored files cannot provide the memo. Missing, changed or malformed input falls back to the original publication validator. Every output inventory, ZIP, GLB, source-byte and poster audit still runs; publication rejection regression tests invoke the original validator directly and are never memoized.

### Poster recipe contract

Each new capture records a versioned input digest binding the GLB and source asset metadata, rendering source (including camera/light/support calculations), runtime/build configuration, capture policy, package/lockfile, pinned Playwright Chromium version. These are raw transparent WebGL PNGs with no text or DOM rasterization, so UI fonts/CSS/HTML are outside the poster recipe. The capture page is isolated from app bootstrap and UI code: it serves only the renderer’s parsed relative import closure, lockfile-pinned Three.js modules and hash-checked catalog GLBs. Unknown network/resources, computed imports, service workers and external capture URLs fail closed. Imported renderer assets, including fonts if later introduced, enter the digest. UI-only changes still select full runtime/browser validation. Pages additionally compares isolated and full-app PNG pixels on the same runner for six samples covering new assets, custom wheel framing, measured support and embedded textures; this does not claim historical provenance for all golden pixels. The generation policy fixes viewport, pixel ratio, dimensions and software-rendering arguments. A custom Chromium version cannot stamp a matching recipe. A fresh build regenerates every non-golden poster, even if a repository-authored receipt claims a matching key: a consistency hash is not generation proof. Golden pairs remain byte-identical; outputs from independently verified GitHub artifact reuse may also be retained. Missing/stale inputs never silently qualify for reuse.

`site/gallery/approved-poster-inputs.json` is an explicit golden-baseline migration for the already reviewed 182 source pairs from PR #24. It binds their existing approved pixels to this recipe boundary; it does not claim to reconstruct unavailable historical generation provenance. If a golden pair's inputs change, CI blocks and requires explicit recapture/review of a new baseline rather than silently replacing approved pixels. It does not change catalog membership, GLB approval or the original immutable reviewed resource seal.

### Measured baseline and expected skipped work

PR #24 [Pages run 39301400965](https://github.com/s010s/lowpoly-vault/actions/runs/39301400965) measured publication checking at 44.711s, Vite at 2.131s, copy/package at 4.676s and the repeated release audit at 46.568s; its 18 serial rejection suites summed to about 504s. A local clean-job trial of this branch ran the first complete publication check (156.859s under concurrent load), then used its valid memo while still auditing all 2,306 output files in 5.724s. A preceding local non-memo audit took 111.201s. These are observations, not promised CI speedups. The former Full release review repeated build/capture/audit in each matrix job; the new graph performs those phases once. In a build with two later output audits, a valid in-job memo avoids two repeated source-publication traversals. An exact-tree main reuse additionally skips rebuilding, recapturing and the already successful PR regression suites, while retaining inventory and deployment smoke. Artifact transfer, runner queues, browser installation and smoke still cost time. The retained `qa/ci-timings` artifacts provide per-run measurements.

The regression matrix covers docs-only, asset addition/removal, shared renderer/config, unknown files, stale/missing poster keys, changed renderer configuration/toolchain/imported fonts, unsupported dependencies and isolated UI bootstrap/style/font separation, a different merge tree, modified validation policy, fork origin, failed/missing check evidence, missing receipts and tampered artifact bytes.

Brand source/browser checks are conditional only on their scripts existing, to allow the independent brand branch to merge in either order. Once present, their failures are blocking; Pages retains `qa/brand-browser` evidence. All `site/*.mjs` test entrypoints are part of the trusted validation-control digest.


## Bounded, exact-coverage CI sharding (2026-10-20)

The long strict-GPU model loop is now partitioned by sorted published ID into at most five deterministic shards (the current 190 models produce five groups of 38). Asset-only selection partitions only the classifier's exact selected IDs. Runtime, policy, unknown-path and missing-provenance changes still select every published model. No classifier exception, assertion, authorization or model acceptance criterion is relaxed. The browser matrix uses at most six concurrent runners, rather than expanding concurrency with every model addition.

Prepare seals the complete shared build's file names and bytes with SHA-256, together with the exact source commit/tree, trusted-control digest, publication manifest digest, runtime configuration and workflow run/attempt. Every browser runner verifies that seal before executing. A separate mandatory model aggregate compares the independently prepared seal with every successful shard receipt and requires exactly the planned union: no missing or duplicate shards/models, no extra IDs, matching GLB hashes, strict-GPU success and the same build/policy/source/runtime/run. Missing, failed, cancelled or skipped selected tasks cannot produce a passing aggregate. These records are evidence of existing functional checks, not human visual review, factual verification or formal profile acceptance.

The 22 existing publication rejection suites are distributed across four isolated GitHub runner filesystems with an exact-coverage aggregate. Each destructive suite still runs its original assertions; suites within a shard remain sequential. This avoids unsafe parallel mutation of a shared checkout and does not cache across tampering cases. Pages deployment requires the publication aggregate as well as its existing build gate. The standalone asset-pipeline workflow retains the same publication requirement.

This stage reduces serial bottlenecks; it does not remove all repeated pre/postmerge work. The independently verified exact-tree/control-plane reuse rules remain unchanged. Publication shards deliberately rerun even when the Pages build is reusable, and Pages versus standalone pipeline validation may still overlap. Batches that add or edit validation scripts/workflows still change the trusted control plane and therefore still require full main validation. Replacing per-batch code with data-only descriptors is a separate authorization-design change, not accomplished by merely moving approval pins into editable JSON.

Measured baseline: [main Pages run 39339026121](https://github.com/s010s/lowpoly-vault/actions/runs/39339026121) spent 1,104 seconds in serial publication rejection checks, and [main Full release review 39339026002](https://github.com/s010s/lowpoly-vault/actions/runs/39339026002) spent about 25 minutes in its single all-model browser test. Those are observed old-run durations, not promised speedups. New-run wall time depends on runner queues, bounded concurrency, preparation, browser installation and the slowest shard; report actual measured runs after the change.

Shard identities bind the workflow run attempt. If a shard must be retried, use **Re-run all jobs** so plan, prepared build and coverage receipts share the new attempt. A failed-jobs-only retry that retains successful old-attempt artifacts is intentionally rejected rather than mixing evidence.


## Incremental render evidence (separate from publication authority)

Strict-GPU interaction, card-WebP reproduction, and gallery-PNG capture are three distinct evidence domains. The first two are separately validated records within the v2 aggregate; the third has its own v1 artifact. All require an independently successful, same-repository main-ancestor run, the exact workflow/check-suite/run attempt, GitHub's immutable artifact digest, and matching protected policy/runtime. Checkout JSON cannot authorize a cache hit. Missing, expired or invalid evidence falls back to fresh validation; it does not approve or revoke a publication.

The model plan independently reconstructs the delivered manifest, complete catalog and all static HTML using protected builders and the saved pre-route Vite template. Shared compiled/runtime bytes and each model's actual GLB, Blend, image, catalog/detail HTML and gallery data enter content keys. The aggregate independently re-fetches the base proof, recomputes current inputs and requires the exact union of actually executed fresh IDs plus verified unchanged IDs. Empty fresh scope is valid only when the entire catalog has valid reused evidence. Every selected shared browser probe and complete publication/inventory gate still runs.

Catalog labels and ownership move to inert JSON, with exact legacy 190-model snapshots and append-only ownership checks. Three frozen revision IDs move to a pure module so the renderer no longer imports the authorization chain for a constant. Only an explicit frozen set of publication-only modules can be outside render policy; importing one into runtime/build/harness automatically protects it again. Unknown executable paths, renderer/harness/browser changes and shared-input changes require full validation. New arbitrary batch-specific code is not automatically incremental.

Poster reuse verifies a separate PNG-only artifact and every pair's input key, SHA-256 and byte count. Historical golden approval records remain immutable; v3 capture orchestration preserves and checks the exact historical harness/renderer recipe. This is compatibility evidence, not new visual approval. A new trusted main baseline is necessary after this infrastructure change. The first baseline still runs all 190 GPU probes and card-WebP reproductions, plus every non-golden gallery capture. Subsequent compatible 190→194 additions select only the four new models, card reproductions and gallery captures when all three proof domains match. The card receipt binds the actual generator/preset/viewer dependencies, pinned browser, GLB and expected shipped WebP bytes. It requires the original successful reproduction report to cover exactly the fresh IDs, with one poster per model and no mismatch; GPU or PNG evidence cannot substitute for it. Missing card evidence causes fresh validation, and zero-fresh plans omit the card renderer only when complete reused evidence exists. Fixtures demonstrate this selection; real-run cache hits must be reported separately after an eligible authorized batch.

The initial implementation rebuilds the shared projection and may repeat the new models after merge. Exact-tree model/poster promotion helpers are not wired into this workflow; Pages retains its separate original exact-tree reuse. It does not promise zero pre/postmerge work or remove catalog-wide integrity, publication mutation tests, representative browser checks or live deployment checks. Generic data-only authorization collectors, owner-dispatched acceptance and durable authorization archives are explicitly outside this change. Existing publication and formal acceptance boundaries are unchanged; no model candidate is published by this infrastructure PR.


### Exact archival inputs and isolated proof production

A fixed literal-only registry may classify complete, SHA-256-pinned source/review bundle members as byte-only archives. It is parsed, never imported or executed, and grants no model acceptance. Owners, candidate/review pins, original payload hashes, regular file modes and complete bundle membership are verified. Only newly added paths belonging to new model IDs may enter this classification; previously declared archives cannot change or disappear. Unknown or actually consumed/executed dependencies remain protected. All existing publication, source-bundle and formal-profile validators still run. The archived generator and QA programs remain intact rather than being omitted or renamed to evade checks.

The full-review workflow now separates publication/build execution from trusted gallery evidence production. A fresh checkout and script-disabled dependency install receive only raw build data and the saved Vite template. Before capture, protected code independently derives the exact delivered manifest, checks source-bound model bytes and audits historical gallery seals. This runner never imports publication collectors. It then captures or independently reuses PNGs, requires complete gallery coverage, independently verifies the entire final built projection, plans GPU/card work and seals the result. A separate downstream runner performs every original complete publication/inventory assertion on its own downloaded copy, verifies that its audit leaves that seal unchanged, and cannot upload a replacement proof or build. Its success remains mandatory for the final aggregate.

This isolation prevents a publication-side program from modifying the browser installation used to mint reusable poster evidence. GPU/card producers and the final aggregate likewise use fresh runners and protected consumer dependencies. The proof binds the sealed Full release review artifact, not byte identity with the separate Pages build. Pages retains its existing full validation, rebuild/capture and live checks; it does not mint the trusted poster baseline.


### Parallel mobile integration

The catalog migration is also checked against mobile source `604531f3c4d49f3c5496a54996a1bc722bb88d01`: all 190 models produce exactly the same 403 static HTML/robots/sitemap files before and after catalog-data injection (combined SHA-256 `044fa712385704028855f0187bf2470fc1ade03ab957c456aedd9531ed060a8b`). The three-model static fixture is rebased to that mobile source only after this independent byte comparison. Legacy catalog/export hashes and all model/gallery bytes remain unchanged. This source-level equivalence does not claim browser acceptance or a successful reusable main baseline; those require the exact integrated CI run.


The isolated deployment audit does not whitelist CI metadata as deployable content. Its protected wrapper verifies the prepared build, retains the exact internal seal bytes and identity in parent-process memory, temporarily removes that one seal while running the unchanged complete audit as a direct Node child, and restores the exact seal even after an audit failure. A replacement seal, unknown deployment member, changed payload or failed audit remains blocking; pre/post workflow verification and the no-upload boundary remain mandatory.

For frozen candidates rooted exactly at `assets/candidates/<collection>/batch-<digits>`, complete archival bundles may additionally preserve members under the exactly matching `production/<collection>/work/<same batch>` source scope. This only derives ownership scope: each member still requires the complete source bundle's exact hash/origin/owner pins, immutable new-ID/new-path registration and protection whenever a trusted consumer reads or executes it. Adjacent batches, other collections, parent directories and unlisted siblings receive no exemption.
